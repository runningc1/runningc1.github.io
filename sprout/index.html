I joined as the main developer on that ERP the week the previous lead developer left, and I split my time between the ERP and production work on a new CNC machine. Monday, October 19, 2026 2026-10-19

Cut each CI run from about 230 seconds to about 62 Live

The test suite now runs in 12 worker processes instead of one. Measuring first showed that one smoke test, which loads all 860 admin pages in a single method, took 157 of the suite's 213 seconds, and a single method cannot be spread across workers. I split it into 12 test classes that each load every 12th page; the totals match the old test exactly.

  • Running in parallel exposed two hidden dependencies between tests, and I fixed both at the source. A cache shared by every test process let one worker read objects that another worker had cached from a different test database; each process now has its own cache. The smoke tests also left their last request stored as the "current request", and a later test picked up a deleted employee from it; that stored request is now cleared after each test.
  • Checked with repeated parallel runs and with one-process runs, using both cache setups, before merging. After the merge, master runs 1,662 tests in 62 seconds, all passing.

Friday, October 16, 2026 2026-10-16

Found why the CNC station pages are slow Analysis

Opening a sheet's work entry at a CNC station took 13 to 22 seconds at the median on three of the machines, against about 1.2 seconds at the kitting stations.

  • Showed from 14 days of request logs that server capacity is not the cause: on average 1.0 to 1.6 of 8 app workers were busy in work hours, and the slow pages are just as slow in quiet hours.
  • Profiled one page open: 6,946 SQL queries, 5,478 of them fetching the same kind of row one at a time (an N+1 query pattern in the serializer).
  • Measured the cost: about 78 minutes of operator waiting per workday across the CNC stations.
  • Wrote the fix plan: golden-response tests and query-budget tests first, then the query fixes, then a staging check and a before-and-after measurement on the floor.

Fixed a nightly inventory sync that had failed silently for five months In review

The nightly job that pushes stock levels from the ERP to the online store had not completed since May. A notification call added in May passed the wrong object, raised an error, and the job's own error handler then crashed, so nothing was reported.

  • Fix records the real error with its traceback and makes the job exit non-zero on failure, so the new job monitor catches it. 5 tests.
  • Held for a business decision: the first good run overwrites any stock counts that were corrected by hand in the store since May.

Made the test suite pass again In review

The ERP's test suite stopped before running any test. I made it runnable, then fixed the 14 tests that were failing because they had fallen behind code changes. Result: 74 tests run, all pass, 2 skipped with written reasons. Test-only changes; no application code touched.

First run: 40 of 54 pages passed; the rest are listed for follow-up.

Thursday, October 15, 2026 2026-10-15

Read-only inventory of the production servers Analysis

Documented the services, scheduled jobs, backups and database on each production server, and got the departing lead developer's answers on everything the servers could not tell me. It found 6 scheduled jobs that fail on every run because the command they call does not exist, with the errors going nowhere.

Monitoring and alerting for the ERP, at no added cost Live

Before this, nobody was alerted when a page threw an error or a scheduled job failed, and nothing checked whether the site was up. Built in-house on the hosting provider's free tools and a Slack app, with no third-party monitoring service:

  • Memory and load alerts on both production servers, routed to Slack and email.
  • An uptime check on a heartbeat page that goes stale if the server or its scheduler stops, plus TLS certificate expiry warnings.
  • An error digest that reads the ERP's existing request log, groups new exceptions, and posts each new group once.
  • A wrapper on all 23 scheduled jobs that records exit codes and alerts when a run fails or does not finish on time.
  • A metrics sampler that keeps server history beyond the provider's 14 days.

The installer and its rollback were tested in a container built from production's configuration (the rollback restores every file byte for byte), then installed on both production servers after midnight on the 16th with a full-system check before and after.

Rebuilt staging to match production Live

The old staging server had not been used since 2023. I rebuilt it so code can be verified on a copy of production before it ships:

  • Same OS release and package versions as production (966 packages identical), and an identical Python environment (205 packages).
  • Restored from production's nightly backup, which also proved the backup restores.
  • Personal data scrubbed on every restore, with a check that stops the app if any real email or phone number remains.
  • Outbound connections from the app blocked at the firewall, so staging cannot email customers or call vendor APIs.
  • A red STAGING bar on every page with a link to the real site.
